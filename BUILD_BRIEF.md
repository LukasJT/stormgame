# Stormwake — AI game build brief

## Give this assignment to the coding agent

Build **Stormwake**, a single-player strategy game where you play as severe weather. The player picks a storm and its birthplace, steers it across a fictional map, and evolves it during the run. Give the player two records to chase before the storm dissipates: the highest death toll and the highest property-damage score. Use the strategic appeal of *Plague Inc.* as inspiration. Create original terminology, map art, interface, sounds, text and balancing.

You are responsible for implementation and playtesting. Work in the supplied project folder. Inspect what is there, preserve existing work, then start building. Complete all four milestones below. Keep the game playable between milestones. If a session ends early, record the last verified milestone, the command to run it, any failing check and the next action in `PROGRESS.md`.

## The first minute

Use this as the design test on a fixed **Normal** forecast. I select **Hurricane** and see two marked origins. **Gull Bank** gives me warm water and room to grow. **Lantern Strait** puts me one move from a port, with less time to gain strength. I pick the strait. On the map I can see my small eye, the port lights, the projected wind footprint, and whether anyone has spotted the storm.

My first choice is **Landfall** or **Hold offshore**. Hovering, tapping or focusing either shows what I stand to gain and lose. If I hold, the eye tightens and strength rises. A bulletin appears: “Lantern Strait storm detected. Lantern Port under warning.” The port's sheltered count begins to climb. If I head inland immediately, I reach the docks with a weaker storm, but fewer residents have had time to take cover. Within 45 seconds at normal speed I can afford an upgrade. Buying **Outer Bands** immediately extends the footprint preview to a neighboring district. On a same-seed replay I can make the opposite opening and see why the totals changed.

## What the player controls

- Build one original regional map with 12–16 named, connected zones. Include warm sea, populated coast, inland plains and cold uplands. Put several town or asset markers in inhabited zones so a narrow track and a wide footprint can hit different things. Use fictional population and property values. Give each storm a season-appropriate starting state on the same geography.
- Offer at least two viable origins per storm, selectable directly on the map and from a labeled list. Preview terrain, strength or fuel advantage, nearest settlement, and one drawback. For tornadoes, contrast an open charging corridor with a short approach to town. For blizzards, contrast an existing snow belt with a wetter upland where snow builds faster. Make these differences affect the simulation.
- Run in pausable real time with 1× and 2× speeds. A route leg takes about 20 simulated seconds. Let the player queue an adjacent destination, inspect an alternative, and see the default drift route if they do nothing. Route previews include expected strength change, exposed towns and current warning level. A route choice is available as soon as the run starts. Open the upgrade panel on pause and restore the prior pause setting when it closes.
- Each storm has strength from 0–100, favorable terrain, a signature action, and a visible footprint. Let the player inspect the local weather forecast alongside the public warning and shelter status described below.
- Pin **Total deaths** beside **Damage score** at the top of the map on desktop and phone. Start the counter at 0 and update it each simulation tick with the cumulative number of people killed across all settlements in the current run. Show the exact whole number with thousands separators. Keep it visible when the player selects a region, pauses or opens upgrades. The selected region can also show its own local toll.
- A run ends at zero strength or when the forecast window closes after five simulated minutes. Display the cause. Show the final **Total deaths** and **Damage score**, a map of the final track, and the hardest-hit settlement. Show when the storm was first detected and how many residents were sheltered when it hit the hardest-hit settlement. Save local bests separately by storm, origin and difficulty in both categories. **Retry same forecast** keeps all three settings and the seed. **New forecast** draws a new seed.

## Detection, public warnings and shelter

1. **First sighting.** Start each storm **Unnoticed**. Check two independent ways for it to be noticed on each simulation tick. A town can spot a storm that passes close, even if it is small. A storm that grows conspicuous enough can be detected at a distance. Give each type its own visibility inputs: touchdown and funnel width for a tornado, strength and band coverage for a hurricane, and the extent of blowing snow for a blizzard. Set the sighting distances and visibility thresholds in balance data. A footprint upgrade can bring detection forward. Show the player the actual cause of the first sighting. Once **Detected**, the storm stays tracked for the run, including when a funnel lifts.
2. **Local warnings.** At detection and whenever the track changes, authorities warn settlements in the projected hazard footprint over the next two route legs. Include outer bands and other hazards that can reach beyond the storm center. Use observed movement and the current committed route when producing the public forecast. Hovering a possible route or inspecting an upgrade is private to the player. Mark each warned town on the map and display its estimated time to impact.
3. **Time to shelter.** Store warning time and sheltered residents per settlement. After four simulated seconds of warning, move residents into shelter gradually, reaching the difficulty's uptake cap after another 20 seconds of continuous warning. Protection applies only to residents already sheltered when a hazard hits. If the track turns, a newly warned town starts its own clock. Residents already sheltered in a town that gets the all-clear stay inside for one leg, then return gradually. Reissuing a warning only moves remaining exposed residents into shelter. Keep sheltered residents within each town's living population.
4. **Player feedback.** Use a single bulletin for first detection and one per local warning change. Selecting a town shows its warning status, arrival estimate, and the number and percentage sheltered. Keep **Total deaths** visible. Apply a lower fatality rate to sheltered residents at impact; calculate property damage from the physical hazard independently. A player should be able to explain why two towns struck by the same storm suffered different death tolls.

## Difficulty changes people and weather

Choose **Easy**, **Normal** or **Hard** before choosing an origin. Show both effects in the selector and lock the choice for that run. These are initial game-balance values. Use the same first-sighting rules on every difficulty so that noticing a storm and deciding to heed a warning remain distinct.

| Difficulty | Residents who heed an official warning, given enough time | Weather along potential routes |
| --- | --- | --- |
| **Easy** | **0%**. Towns receive and display advisories, but residents ignore official shelter instructions. | Aim for 65% favorable, 25% neutral and 10% hostile route conditions. Most routes sustain a storm. |
| **Normal** | Up to **50%** take shelter. An early warning can protect half a town. | Aim for 45% favorable, 35% neutral and 20% hostile. Some detours pay off. |
| **Hard** | Up to **90%** take shelter. Lead time matters even with high compliance. | Aim for 25% favorable, 40% neutral and 35% hostile. Good conditions come in shorter stretches. |

Apply those weights to the seeded local weather for each zone and forecast period. Preserve geography and the advertised advantage of each origin across difficulties. Favorable conditions mean **warm water** that builds hurricane strength, **unstable air** that replenishes a supercell's rotation, or **cold, moist air** that adds to snowpack. Hostile conditions mean **cooler water** that stalls hurricane growth, **stable air** that slows rotation recovery, or a **thaw** that breaks a snowy corridor. Show the effect in the route preview, for example “Coldwater Shelf · cooler water · no strength gain this leg.” Preserve at least one viable opening route per origin on Hard. Keep the damage and fatality formulas identical across difficulties.

**Acceptance checks.** In a controlled scenario with 1,000 living residents, identical storm intensity, and 24 seconds of uninterrupted warning before the first hit, verify 0 / 500 / 900 residents sheltered on Easy / Normal / Hard. Property loss should be identical and the death toll should fall as shelter uptake rises. In a second test, redirect a detected storm and verify that a newly warned town gets its own response time. Also test first detection by proximity alone and by storm growth alone. Separately, compare the same set of seeds, origins and route samples across difficulties for each storm. Verify Easy has more favorable segments than Normal and Normal more than Hard, each storm's fuel responds to those conditions, and all Hard origins have a viable opening. Save and resume during an active warning and check the next tick matches an uninterrupted run.

## Three storms and their upgrades

Each storm gets three upgrade branches with two purchases each. The second purchase requires the first. The three advanced purchases are mutually exclusive within a run. Keep the other basic purchases available. Show costs, prerequisites, lock reasons and exact effects before spending. The values below are starting points for playtesting.

| Storm | Signature decision | Three branches, basic → advanced |
| --- | --- | --- |
| **Hurricane** | Hold over warm water for one leg to build strength, or move toward land. The core weakens inland. Outer wind and rain can reach beyond the eye. | **Warm Core** gains strength faster offshore → **Inland Reserve** halves strength loss on the first two inland legs. **Outer Bands** adds a neighboring zone to the fringe → **Trailing Rain** leaves one leg of weaker rain behind. **Coastal Surge** adds a pulse of property damage on landfall → **Surge Fan** extends that pulse to a second connected coastal zone. |
| **Tornado** | Steer a parent supercell. **Touch down** to draw a narrow damage track through individual sites. Ground contact spends rotation, and **Lift** lets rotation recover while the cloud keeps moving. Mark the track where the funnel actually traveled. | **Wide Funnel** widens the track → **Satellite Vortex** traces a second, offset track. **Stable Inflow** slows rotation drain → **Long Track** carries a surviving touchdown through the next route bend with a one-time rotation refill. **Cycling Cell** recharges faster aloft → **Rapid Reformation** lets a fully recharged cell bank one extra touchdown charge. |
| **Blizzard** | Lay a band of snow, then trigger **Whiteout** across connected snowy zones. Spending snowpack now gives immediate impact. Waiting can connect another settlement, but warmth can break the chain. Preview exactly which zones qualify. | **Snow Bands** lays snow faster → **Backbuilding** also lays snow in the previous zone for one leg. **Powder Reserve** reduces snowpack spent per whiteout → **Second Gust** sends one weaker follow-up pulse through zones that still hold snow. **Deep Freeze** slows melting → **Frozen Corridor** preserves one link through a warm zone for one leg. |

Represent each footprint differently on the map: a spiral with a broad outer ring, a funnel with a thin ground scar, and a band of hatched snow with gusts moving along it. The footprint preview and actual impact must use the same geometry or zone-selection rules. An upgrade purchase should change a decision, a footprint, or the result of a repeatable encounter.

## Economy and scoring

- **Strength** keeps the storm alive. **Momentum** buys upgrades. **Damage score** measures losses. Show them with distinct labels and units. Start with 3 Momentum and add 1 every 30 simulated seconds. Give 1 exploration bonus for each of the first four distinct zones entered after the origin. Price basic upgrades at 4 and advanced upgrades at 8. This gives the player a first purchase within 30 seconds even offshore. A full run earns at most 17, enough for two basics and one advanced purchase. Show the time to the next point.
- At each simulation tick, intersect the active hazards with settlement sites. Calculate fatalities using hazard intensity and the site's living exposed and sheltered populations. Calculate property losses using hazard intensity and remaining asset value. Track integer fatalities and property loss, preserving fractional progress between ticks where needed. Multiple hazards can hit one site, but total losses must stay within what was present. Empty sea has zero direct losses.
- Award **one damage point per $100,000 of total property destroyed**, rounded down once on the run total. For example, $350,000 lost at the docks plus $170,000 inland yields **5 points**. Derive **Total deaths** by summing the settlements' cumulative fatalities so revisiting a town or loading a save counts each death exactly once. Shelters can change the death toll even when property loss stays high. Make the results screen show enough numbers for the player to reconstruct the score.
- Store all tuning values together. Start with two simple strategies per storm and replay both across ten fixed seeds. Check that every origin can buy an early upgrade, both immediate impact and delayed buildup can pay off, and no idle loop yields unlimited points. If one opening wins every comparison, adjust the tradeoff and rerun. Record one example seed and the observed results.

## Implementation rules

1. Target a modern desktop browser first, with touch and keyboard controls that also work on phones. In an empty project, use Vite with its vanilla TypeScript template, strict TypeScript, an inline SVG map and HTML controls. Use Vitest for rules and Playwright for player journeys. Resolve mutually compatible stable versions and commit a lockfile. The game should run locally without accounts, API keys, live weather feeds or a server-side database.
2. Keep map and upgrade definitions in data files. Keep the simulation independent of the browser. Give it an initial seed, a fixed tick, and commands such as `chooseRoute`, `activateAbility` and `buyUpgrade`. The UI sends commands and renders the resulting state. Use the same rules for preview and execution. Give visual effects their own randomness so changing a particle animation cannot change a score.
3. Advance game rules in fixed steps and interpolate only the visuals. At 2× process twice as many simulation ticks. Pause when the tab is hidden and discard the time spent away. Persist the seed, difficulty, random-generator state, simulation tick, environmental forecast, discovery state, route progress, active hazards, per-town warning timers and sheltered counts, site balances and purchases. Resume paused. If a saved run is unreadable, explain that briefly and offer a fresh run. Store records separately.
4. Make all critical controls reachable by keyboard and touch. Pair map colors with symbols or patterns; give selected routes and storm footprints distinct styles. Support reduced motion. On a phone, let the map stay visible above a compact action sheet. Give a new player one contextual hint at a time.
5. Provide `npm run dev`, `npm run typecheck`, `npm test`, `npm run test:e2e` and `npm run build`. Write unit tests for identical seed + tick-stamped inputs producing identical outcomes, speed invariance, correct scoring, stock limits, purchase validation, and save/reload equivalence. Use browser tests for selecting an origin, steering, activating a signature action, buying an upgrade and seeing its effect, finishing, and replaying. Use player-visible controls and assertions. Inspect at least one completed run visually.
6. At handoff, provide the actual launch commands, required runtime version, test results, a reproducible example run and any known limitations. Report which browser and viewport sizes you actually checked. Work through the milestones autonomously and claim a check passed only after running it.

## Research behind these choices

- **Build a whole playable loop early.** Anthropic's long-running agent experiments found that a feature checklist, incremental implementation, browser verification and short handoff notes helped agents resume complex web projects. Here, the first checkpoint is an entire hurricane run so we can test a strategic decision while changes are still cheap. [Anthropic’s engineering report](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)
- **Use a map the agent can play.** Vite supplies a development server and a static production build. SVG exposes individual map elements to browser events. For this small regional strategy map, my recommendation is SVG for geography and HTML for controls so a human and a browser test can select the same named origin. Playwright recommends testing the behavior users see. [Vite guide](https://vite.dev/guide/) · [MDN on scripting SVG](https://developer.mozilla.org/en-US/docs/Web/SVG/Guides/Scripting) · [Playwright testing guidance](https://playwright.dev/docs/best-practices)
- **Make strategy comparisons reproducible.** Glenn Fiedler explains how a fixed simulation step separates game behavior from the rendering frame rate. Combining that with a saved seed and tick-stamped commands makes same-forecast replays and automated balance checks practical for this game. [Fix Your Timestep!](https://gafferongames.com/post/fix_your_timestep/)
- **Give each storm one weather idea players can recognize.** Warm ocean water fuels tropical cyclones, a rotating updraft is central to a supercell, and wind can lift previously fallen snow into a ground blizzard. Offshore holding, touchdown charges and connected whiteouts are original game rules built around those observations. [NOAA on hurricanes](https://www.nesdis.noaa.gov/about/k-12-education/severe-weather/how-does-hurricane-form) · [NOAA on tornadoes](https://www.nssl.noaa.gov/education/svrwx101/tornadoes/types/) · [National Weather Service on blizzards](https://www.weather.gov/fgz/WinterStorms)
